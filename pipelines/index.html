    Two engines, one verdict

    The same gate has to hold whether a service builds on GitLab CI or on the Jenkins jobs that predate it. So the rules live in one place, and each engine calls it. Switch the engine above and the log format changes. The decision does not.

    Why you should not trust the animation

    A page that draws green ticks can draw anything. This one is checked two ways, and both are public.

    The answers come from Groovy

    rules/fixture.json is written by shared-library/test/run-fixture.groovy running the real classes. The JavaScript port can only match it. If both sides were allowed to author the file, agreement would prove nothing.

    The copy is checked against upstream

    This page vendors two files from the repository. CI compares their SHA-256 against what the repository serves, so a stale copy fails the build instead of quietly becoming a second implementation.

    Two bugs it already caught

    The fixture found a duplicate-service message that named the count instead of the service id, and it found that my first truthy() let a missing SBOM through. Neither was caught by the tests that were already passing.

    Read the rules themselves

    The interesting part is not the animation. It is ReleaseRules.groovy, GateResult.groovy and DeploymentPlan.groovy, and the thirty cases that hold them in place.
